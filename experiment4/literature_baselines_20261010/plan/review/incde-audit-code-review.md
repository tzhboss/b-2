## Concrete findings

1. **[P1] Legal earliest early stopping is rejected (audit lines44–46).** Native `repos/IncDE/main.py:249–257` logs `Early Stopping! Snapshot:s Epoch: 31 ...` and breaks before the normal epoch31 log. The regex requires `Epoch:` immediately followed by digits, so it misses the early-stop line; normal logs stop at30 and `max(epochs)>30` is false. A synthetic CPU fixture reproduces this false rejection. Controller fix: parse both normal epochs and explicit early-stop terminal epochs, allowing native epoch31 stop; distinguish a max200 completion (last zero-based epoch199) from an author early stop. Validate the frozen defaults, no-debug setting, sequence and terminal evidence instead of using this threshold alone. A selected best checkpoint can legitimately come from an earlier epoch; do not require its epoch_id>30.

2. **[P2] Metric recomputation does not preserve native float32 batch accumulation (lines58–59,82).** Author `src/model/model_process.py:226,293–320` uses batch100, casts ranks to float32, sums reciprocal ranks per batch, adds Python floats, then rounds4. Audit computes NumPy whole-array float64 means and rounds4. Its limitation string claiming native float32 accumulation is retained is incorrect. CPU fixture ranks `[1]*2501 + [3]*7498 + [6]` give native MRR `0.5000500183105469` -> `0.5001`, versus float64 `0.50005` -> `0.5000`. This proves the per-task rounding contract differs, not that any current job has a mismatch. Such a difference can propagate across aggregate rounding boundaries. Controller fix: keep high-precision independent metrics, and separately reproduce batch100 float32 arithmetic in native query order on the original evaluation device when asserting exact native logs. Do not call a floating-point contract difference rank corruption. Hits counts are integer counts and unaffected by this reciprocal-sum issue.

3. **[P2] The integrity trust chain ends at run-local declarations (lines15–21).** The checker reads `registered-job.json` and its digests but never compares them to the frozen master entry, protocol digest, runtime command/cwd/GPU mapping, dataset/seed/source_commit. Current four copies were independently checked and match; this finding is a prospective acceptance gap, not evidence of substitution. Controller fix: select exactly one entry by job ID from the frozen manifest, compare the full job, then validate only authorized runtime path substitutions and record hashes of both manifests. Hashing a self-declared manifest after reading it does not establish its frozen identity. The existing skip for regenerated `train_sorted_by_edges_betweenness.txt` is narrow and documented; raw train/valid/test must remain bound to registration.

4. **[P2] Filename/metadata/schema and native order contracts are incompletely asserted (lines40–59,75–76).** Exact19 filenames are checked, but embedded trained/tested snapshot IDs are not checked against filenames or `0 <= tested <= trained < 5` / exact pre-FWT pair. For example exchanging `train1_test0_post_train.npz` and `train2_test0_post_train.npz` preserves the filename set and query contract; the loop uses embedded IDs, so metadata and matching checkpoint continue to agree despite misleading filenames. No explicit scalar-int metadata, 1D integer/equal-length arrays, exact row count or checkpoint embedding dimension/dtype/finite-value checks exist. Counter comparison deliberately loses query order: native `KnowledgeGraph.fact2id(order=True):334–343` sorts test triples by even relation ID, preserves within-relation order; `TestDataset:141–144` emits all forward queries then all inverses. Audit constructs raw file-order queries. Query permutation with attached ranks does not alter exact mathematical metrics or sampled replay, but it prevents native batch arithmetic/order validation. Controller fix: parse filenames into expected metadata, check shapes/types/bounds before indexing, reconstruct sorted native query order, and fail cleanly before dependent replay if structural checks fail. Accumulating a failed ck then continuing into invalid metadata can throw without writing a FAIL report.

5. **[P2] Five checkpoint filenames do not establish validation-best selection (lines47,60–71).** The replay shows sampled ranks agree with whatever checkpoint is named best; it does not check epoch_id, source checkpoint identity, or that the saved epoch was selected by native strict validation-MRR improvement. Native `main.py:241–248,266–278` saves each epoch and copies a best checkpoint; `:156–160` reloads it. Controller fix: validate the exact snapshot0–4 best names, epoch_id bounds/normal-or-stop training history, selected epoch against available native best-update evidence, and identical selected checkpoint bytes where retained. Because normal validation logs are rounded and the early-stop branch omits a normal epoch log, those logs alone cannot fully certify an unrounded strict improvement/tie decision; disclose this residual limitation rather than inventing validation precision.

6. **[P2] Aggregate log parsing is not anchored to the final report table (lines43,78–80).** It only checks marker presence, scans all numeric table rows, and takes the last match per snapshot. Ordinary native output makes the intended table last, so no observed mismatch is asserted. Stale appended rows or another matching table can satisfy this check. Controller fix: isolate the final `Report Result:` block, verify header order `Snapshot, Time, Whole_MRR, Whole_Hits@1, Whole_Hits@3, Whole_Hits@10`, exactly five distinct rows0–4, then compare reconstructed aggregates. Parse the final per-test-task results as well if claiming all15 task metrics match logged values; the current checker only asserts overall rows.

## Contracts that agree with released source

- IDs: first seen across snapshot train -> valid -> test; h before t; relation/inverse consecutive even/odd. Author `KnowledgeGraph:247–252` reassigns raw train.txt after trying the sorted layer input, so raw training-file order is the actual ID contract. Independent audit construction agrees. Existing entity2id/relation2id files are not authoritative for this constructor.
- Candidates: tested snapshot t's entity prefix, even when using trained snapshot s>=t. `BaseModel.predict:104–111` and audit lines54,68 agree. These native historical evaluations do not introduce later competitor entities.
- Filters: cumulative train+valid+test truths through tested snapshot t, forward and inverse. Labels are built from `kg.snapshots[t].hr2t_all`; the unused `hr2t` variable at model_process.py:240 does not change label selection. filtered_count includes the target before restoration; audit set lengths agree.
- Independent score/rank replay: p2 normalization; float64 native embeddings; `sigmoid(9 - L1(h+r-alltails))`; mask true alternative tails to -10000000 and restore target; descending argsort followed by inverse argsort. Audit does not call the author's predictor/evaluator. Native tie behavior depends on torch/device argsort; a different-device discrepancy needs investigation rather than a changed tie rule.
- Two-stage embedding: `DLKGE.embedding:170–187` returns current embeddings when runtime args.epoch>20. Native training ends after30 or reaches199, and `main.py:280–284` loads only state_dict, not args.epoch. Therefore replaying raw selected ent/rel weights is correct even when best checkpoint epoch_id<=20. Do not replay with the selected checkpoint's epoch substituted into runtime args.epoch. Active snapshot_post_processing is the inherited no-op; the DLKGE alternative is commented.
- Native aggregation: each test-task metric is rounded4, weighted by that task's test-triple count, then rounded3 in `main.py:202–222`. Audit query-count weights are equivalent because every test triple has forward and inverse queries. The float32 arithmetic issue above remains separate.
